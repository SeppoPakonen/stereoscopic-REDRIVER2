## Goal

Expose the configurable internal resolution (from T0.4) as a user-facing option,
so the game can render sharply above the PSX-native 320x240.

## Scope (adjusted with the owner)

The as-written T3.3 ("wire `-res`/config.ini + launcher GUI and verify in the
running game") requires the game/launcher integration. Per the owner's decision
(same as T1.6–T3.2), T3.3 is scoped to the verifiable slice: a **headless
harness** that renders a perspective probe scene at several internal
resolutions (320x240, 640x480, 1280x720) and proves the DX11 renderer's
internal-resolution rendering is **projection-correct at every resolution** —
the perspective centre stays at the screen centre (which the legacy PSX path
could not do at non-native res) and the captured offscreen dims match the
configured resolution. The `-res`/config.ini/launcher wiring is a later
integration/UI task.

## Context

The DX11 renderer builds its own projection (T0.4/T1.1), so internal resolution
is already free; T2.1 already verified the offscreen RTs at 320x240 and 480x360.
The legacy limitation was that rendering the offscreen at window size broke the
3D projection — the perspective centre landed in the top-left (the 320x240
lock). The DX11 path must not reproduce this: the projection uses the configured
internal aspect, so the perspective centre stays centred.

## Design

`spike/dx11_ires_test.cpp` (game-agnostic, on the full DX11 stack), for each
internal resolution in `{320x240, 640x480, 1280x720}`:

- renders a **symmetric pair of vertical marker bars** (red at world `x=-a`,
  blue at `x=+a`, depth `z=-d`) into the offscreen RT (identity camera);
- captures the RT and verifies:
  - `IRES` — the captured dims equal the configured internal resolution;
  - `PROJ` — each bar's rendered centre column matches the analytic projection
    `col(x) = ((f/aspect)·x/(1-d) + 1)/2 · iW` (the projection is correct, not
    resolution-dependent);
  - `SYMM` — the rendered left/right bar centres are symmetric about `iW/2`
    (no top-left perspective-centre shift at higher res).

## Verification

`premake5 gmake2 --cc=gcc` + `mingw32-make dx11_ires config=release_x86`
(32-bit; mingw32 runtime DLLs beside the exe). Run `bin/Release/dx11_ires.exe`.
Writes `dx11_ires_result.txt` (ires / projection / symmetry probes).

### Actual observed output (mingw32 32-bit, release_x86)

```
dx11_ires_result.txt:
   IRES 320x240  captured 320x240 PASS
   IRES 640x480  captured 640x480 PASS
   IRES 1280x720 captured 1280x720 PASS
   PROJ 320x240  left=107(exp108) right=211(exp212) PASS
   PROJ 640x480  left=215(exp216) right=423(exp424) PASS
   PROJ 1280x720 left=483(exp484) right=795(exp796) PASS
   SYMM 320x240 left=107 right=211 symmetric PASS
   SYMM 640x480 left=215 right=423 symmetric PASS
   SYMM 1280x720 left=483 right=795 symmetric PASS
   TOTAL_FAILS=0 IRES=PASS
```

The DX11 renderer renders the perspective probe scene correctly at every
internal resolution: the captured offscreen dims match the configured
resolution, the marker centres land within 1px of the analytic projection
(bar-centre scan rounding), and the left/right markers stay symmetric about the
screen centre — i.e. the perspective centre does **not** shift to the top-left
at higher res (the legacy 320x240 lock's failure mode). The projection is built
from the configured internal aspect, so higher-res rendering is inherently sharp
and correct.

### Bugs found and fixed during verification

One harness bug: iterating multiple resolutions by creating/destroying each
renderer mid-loop posted `WM_QUIT` to the thread message queue, which the next
window's `BeginFrame` picked up and the loop broke after the first resolution.
Fixed by creating all renderers upfront and destroying them at the end. The
renderer/projection modules themselves were correct — the existing T0.4/T1.1
projection already scales with the internal resolution (verified at 320x240,
640x480 and 1280x720).

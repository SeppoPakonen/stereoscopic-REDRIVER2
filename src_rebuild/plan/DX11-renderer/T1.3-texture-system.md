# T1.3 — Texture system: VRAM/tpage/clut → DX11 SRVs

|            | |
|------------|-|
| **Phase**  | Phase 1 — Core DX11 renderer |
| **Milestone** | M1 — Core DX11 renderer |
| **Status** | done |

## Goal

Translate the PSX texture model (1024x512 VRAM, tpage/clut) into DX11
shader-resource views, reusing the existing tpage/clut decode math so visuals
match the legacy path.

## Context

Textures are paletted TIM data in a 1024x512 VRAM; `texture_pages[128]` /
`texture_cluts[128][32]` decode engine texture-set/id → tpage/clut. The legacy
path uploads the whole VRAM into one GL texture and samples via tpage/clut UVs
with a shader-side palette decode + an RG8 LUT. The DX11 renderer must decide
between a single VRAM atlas SRV vs. per-texture SRVs, keeping the decode math
(`GET_TPAGE_FORMAT`, `GET_CLUT_X/Y`, 4/8-bit palette LUT) so output matches.

## Scope note: delivered as a standalone module + harness (like T1.1 / T1.2)

The texture system is `spike/dx11_textures.{h,c}` (game-agnostic), driven by
`spike/dx11_textures_test.cpp` on top of the `dx11_renderer` foundation. It is
adopted into the game draw-command renderer in T1.5 alongside the foundation
window/swapchain module and the T1.2 resource manager.

## Design decision: per-texture CPU-side bake to RGBA, not a VRAM atlas

The legacy `psyx` path keeps the whole 1024x512 VRAM as one GL texture and
decodes the palette in the fragment shader (sampling the VRAM texture, pulling
a palette index, then re-sampling the CLUT region, then BiLUT/`rgLUT` to expand
RGB555 → RGBA). This is a GL-specific shader trick (it even relies on a
peculiar `*255` CLUT offset in the VRAM texture layout).

The DX11 renderer instead **bakes each paletted tpage region to its own
R8G8B8A8_UNORM texture on the CPU at upload time**, using the exact same
decode math the GL shader implements:

- `GET_TPAGE_FORMAT(tpage) = (tpage >> 7) & 0x3` → 4-bit / 8-bit / 16-bit.
- tpage position: `X = (tpage << 6) & 0x3c0`, `Y = ((tpage << 4) & 0x100) + ((tpage >> 2) & 0x200)`.
- `GET_CLUT_X(clut) = (clut & 0x3f) << 4`, `GET_CLUT_Y(clut) = clut >> 6`.
- 4-bit: 4 pixels per 16-bit VRAM word (2 bytes × 2 nibbles; pixel `x` → byte
  `(x & 2) >> 1`, nibble `x & 1`, low nibble = even pixel).
- 8-bit: 2 pixels per word (low byte = even pixel, high byte = odd pixel).
- Palette index → CLUT word at `vram[clutY * 1024 + clutX + index]`.
- RGB555 → RGBA (the `rgLUT` expansion): `R=(c&31)<<3`, `G=((c>>5)&31)<<3`,
  `B=((c>>10)&31)<<3`, `A=255` (the stp bit → semi-transparency is a draw-time
  blend concern, out of scope here).

A single 1x1 white texture substitutes for untextured surfaces (the
`g_whiteTexture` analogue).

**Why per-texture SRVs over a VRAM atlas:** baking once at upload is simpler
and faster at draw time (a plain point-sampled texture fetch, no shader palette
decode), produces identical output (same decode math), avoids the GL atlas's
`*255` CLUT storage quirk, and gives each texture a clean, self-describing SRV
that the draw-command renderer can bind per material with no VRAM-coordinate
bookkeeping. The atlas approach would only pay off if most of VRAM changed
every frame (it does not — textures are uploaded once when a level loads).

## Steps

- [x] Port the VRAM staging path (`GR_CopyVRAM`) into the module: a 1024x512
      `u16` staging array + `Dx11Tex_CopyVRAM` (same semantics: copy a w×h u16
      region from src into the VRAM at a destination).
- [x] Port the tpage/clut decode (`GET_TPAGE_FORMAT`, tpage X/Y,
      `GET_CLUT_X/Y`, 4/8-bit nibble/byte extraction, CLUT lookup, RGB555→RGBA)
      to a CPU `DecodeToRGBA` that bakes a paletted region into RGBA.
- [x] Handle 4-bit and 8-bit paletted formats (verified separately) plus the
      16-bit direct-RGB555 path, and a white 1x1 untextured substitute SRV.
- [x] Create/cache an `R8G8B8A8_UNORM` texture + SRV per baked region
      (keyed by tpage/clut/texX/texY/w/h), and expose `GetSRV` for binding.
- [x] Verify a textured quad renders and the decoded colors match the expected
      palette (read-back asserted against the chosen palette in the harness).

## Acceptance criteria

- [x] Textured geometry renders with correct tpage/clut colors in DX11.
- [x] 4-bit and 8-bit paletted textures both work (read-back + BMP).
- [x] Visual output matches the `-renderer psyx` reference for the same scene
      (same RGB555→RGBA decode math; full in-game A/B is deferred to T1.6, the
      harness proves the decode produces the identical palette colors here).

## Verification

Built with `premake5 gmake2 --cc=gcc` + `mingw32-make dx11_textures
config=release_x86` (32-bit, matching REDRIVER2.exe; needs the mingw32 runtime
DLLs beside it).

Run: `bin/Release/dx11_textures.exe -res 800x600`. Writes relative to the exe:

- `dx11_textures_frame.bmp/.txt` — backbuffer capture (two quads, one per
  texture, distinct colors → both SRVs bound and rendered).
- `dx11_textures_bake_4bit.txt` / `dx11_textures_bake_8bit.txt` — read-back of
  the baked RGBA textures (first rows) so the decode can be asserted.
- `dx11_textures_result.txt` — PASS/FAIL assertion of the decoded colors
  against the expected palette (white/red/green/blue checker).

### Actual observed output (mingw32 32-bit, release_x86)

```
dx11_textures_result.txt:  4-BIT mismatch=0  px(0,0)=248,248,248,255 px(1,0)=248,0,0,255
                           8-BIT mismatch=0  px(2,0)=0,248,0,255    px(3,0)=0,0,248,255
                           TOTAL_MISMATCH=0 DECODE=PASS
dx11_textures_frame.txt:   brightPix=480000 bbox=(0,0)-(799,599) Rrange[0,248]  (800x600)
```

Both the 4-bit and 8-bit paletted regions bake to the exact expected colors
(white/red/green/blue checker = RGB555 0x7FFF/0x001F/0x03E0/0x7C00 → 248,248,248
/ 248,0,0 / 0,248,0 / 0,0,248), and the two quads (one per SRV) render the full
backbuffer with both color sets present. Decode matches the `psyx` RGB555→RGBA
math.

### Bugs found and fixed during verification

1. **Harness data bug: the 8-bit texture used `tpage=1`, which has format bits
   `(1>>7)&3 = 0` (4-bit).** The bake correctly honoured `GET_TPAGE_FORMAT` and
   decoded the region as 4-bit, so every pixel read index 0 → all white. Fixed
   by using `tpage=0x81` (format 1 via bit 7 + tpX=64 via bit 0) for the 8-bit
   texture. This confirmed the module's format handling is correct — the error
   was in the test data, not the decode.
2. **`ID3D11PixelShader *ps` was declared on the same line as `vs`, so it was
   typed as `ID3D11VertexShader*` (compile error).** Fixed by declaring `vs` and
   `ps` separately.

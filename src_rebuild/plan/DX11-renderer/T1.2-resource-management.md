# T1.2 — Resource management (VB/IB, CBs, SRVs, arena)

|            | |
|------------|-|
| **Phase**  | Phase 1 — Core DX11 renderer |
| **Milestone** | M1 — Core DX11 renderer |
| **Status** | done |

## Goal

Implement DX11 resource management: vertex/index buffers, constant buffers,
shader-resource views, sampler state, and a per-frame arena that backs the
draw-command list and its vertex data.

## Context

The draw-command list (T0.2) is per-frame. The renderer needs a way to pack
world-space vertices into GPU buffers and bind per-draw state (world transform,
material, camera) via constant buffers. A per-frame arena lets the game submit
commands/vertices each frame without per-object allocation.

## Scope note: delivered as a standalone module + harness (like T1.1)

The resource manager is `spike/dx11_resources.{h,c}` (game-agnostic), driven by
`spike/dx11_resources_test.cpp` on top of the `dx11_renderer` foundation. It is
adopted into the game draw-command renderer in T1.5 alongside the foundation
window/swapchain module.

## Steps

- [x] Per-frame arena allocator for the draw-command list vertex data (growable,
      cleared each frame, geometric growth up to a hard cap).
- [x] Vertex buffer (dynamic/update) + index buffer management for submitted
      geometry (world-space vertices from the `MODEL` meshes; the VB is
      `D3D11_USAGE_DYNAMIC` + `WRITE_DISCARD`, reused every frame).
- [x] Constant buffer layout (world/view/projection per eye, material params,
      camera) and per-draw binding — a per-draw world-CB pool (one 64-byte
      DEFAULT CB per slot, updated via `UpdateSubresource`) + a view/proj CB.
- [x] SRV + sampler management (default point sampler + `BindSRV`; textures
      themselves are T1.3).
- [x] Cleanup/free paths (device teardown; the arenas/dynamic buffers are
      reused across frames with no per-frame allocation).

## Acceptance criteria

- [x] The game can submit N draw commands with vertices each frame into the
      arena (verified: 24 draw commands / 96 verts / 144 indices per frame).
- [x] Per-draw VB/CB binding works; buffers are reused without per-frame leaks
      (verified: 40 frames, arena capacity stable, `totalVerts` bounded).
- [x] Frame-over-frame allocation is bounded (verified: `boundedGrowth=YES`).

## Deliverables

- `spike/dx11_resources.h` / `spike/dx11_resources.c` — vertex arena +
  dynamic VB/IB, per-draw world-CB pool + view/proj CB, default sampler + SRV
  bind, bounded-growth stats, backbuffer-capture-independent `DebugDump`
  (read-back of uploaded VB + view-proj for verification).
- `spike/dx11_resources_test.cpp` — harness that each frame submits a grid of
  draw commands (a quad = 4 verts + 6 indices + one world-CB slot each),
  uploads them, draws every command with its own world slot, samples a
  checkerboard SRV, captures the backbuffer to BMP, and records per-frame
  arena-capacity stats to prove bounded growth.
- `premake5.lua` — new `dx11_resources` project (compiles the renderer +
  resources modules + harness; links d3d11/dxgi/d3dcompiler/user32/gdi32).

## Design note: per-draw world CB pool, not a VSSetConstantBuffers1 arena

The first CB design used a single big dynamic CB bound per-draw with
`ID3D11DeviceContext1::VSSetConstantBuffers1` (a slot offset). At runtime this
rendered nothing (the shader read a wrong/zero world matrix -> degenerate
quads). It was replaced with a **pool of small per-draw world CBs**, one per
slot, updated via `UpdateSubresource` and bound with plain `VSSetConstantBuffers`
— verified working. This is bounded (fixed `cbSlots` count) and simpler.

## Verification

Built with `premake5 gmake2 --cc=gcc` + `mingw32-make dx11_resources
config=release_x86` (32-bit, matching REDRIVER2.exe; needs the mingw32 runtime
DLLs beside it).

Run: `bin/Release/dx11_resources.exe -res 800x600`. Writes relative to the exe:

- `dx11_resources_frame.bmp/.txt` — backbuffer capture (frame 0, before
  Present/DISCARD).
- `dx11_resources_stats.txt` — per-frame arena capacity + a `boundedGrowth`
  conclusion.
- `dx11_resources_dbg.txt` — first-upload vertex/view-proj dump.

### Actual observed output (mingw32 32-bit, release_x86)

```
dx11_resources_frame.txt:  brightPix=212064 bbox=(93,97)-(706,502) Rrange[31,255]  (800x600)
dx11_resources_stats.txt:  frame=0 verts=96 idx=144 vertCap=128 cbSlotsUsed=24
                           ...
                           stableFrames=39 boundedGrowth=YES totalFrames=40 totalVerts=3840
```

The 6x4 quad grid (24 per-draw world-matrix slots) renders across the screen
with per-quad world transforms and the checkerboard texture sampled through the
default sampler. The vertex arena grows from its initial 64 to 128 (for 96
verts) on frame 0, then stays at 128 for all 40 frames — allocation is bounded
and there are no per-frame leaks.

### Bugs found and fixed during verification

1. **`cbViewProj` created with `CPUAccessFlags = WRITE` on a DEFAULT buffer →
   `E_INVALIDARG`.** The `D3D11_BUFFER_DESC` was reused from the dynamic buffer
   setup, leaving `CPUAccessFlags = WRITE`. A DEFAULT constant buffer must have
   `CPUAccessFlags = 0`. (This also silently broke the earlier "render" runs:
   the view-proj CB was being created as a dynamic buffer updated via
   `UpdateSubresource`, which is invalid, so the projection was never applied.)
2. **Arena crash: `vertCap` set but the vertex array never allocated.** Setting
   an initial capacity without allocating `verts`/`inds` made the first
   `PushVertex` dereference NULL. Fixed by allocating the initial arenas in
   `Dx11Res_Create`.
3. **Cleanup `goto`s crossing variable initializations** (GCC error). Hoisted
   all locals to the top of `Dx11Res_Create` before any `goto`.
4. **`VSSetConstantBuffers1` slot binding rendered nothing** (see design note) —
   replaced with a per-draw world-CB pool.

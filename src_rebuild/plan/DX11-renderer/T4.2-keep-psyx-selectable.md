## Goal

Keep the legacy PsyX/PsyCross GL renderer (`-renderer psyx`) compilable,
selectable and functional as the reference/fallback backend while the DX11
renderer becomes the default — and prove the two backends are **cleanly
separated** (the DX11 binary contains no psyx code, and vice versa) and can be
A/B'd from the **same world-state** via an emulator-style store/load.

## Scope (adjusted with the owner)

The as-written T4.2 ("run a mission under `-renderer psyx` and confirm identical
legacy output") is blocked in this environment: the full game does not reach the
gameplay loop headless, and the full `DrawGame` → draw-command → DX11 → per-eye
→ composite path is a later integration task, so a full-game pixel A/B is not
possible yet. Per the owner's decision, T4.2 is scoped to two deliverables:

1. **Separate backend binaries** — `dx11_backendab_psyx` (links only the
   PsyCross GL backend: GTE + addPrim + `DrawOTag`) and `dx11_backendab_dx11`
   (links only the DX11 draw-command stack). The DX11 binary contains **no psyx
   code**; the psyx binary contains **no DX11 code**.
2. **Emulator-style store/load A/B** — both binaries implement a
   `-store <state> -shot <bmp>` / `-load <state> -shot <bmp>` contract: in one
   "engine iteration" they render a common screen-space scene and save the
   **world-state + a screenshot**; in the other backend they **load the state
   and render immediately (no engine iterations)** to a screenshot. A compare
   step proves both backends reproduced the same scene (same quads, same
   colors, same screen positions) from the identical stored state.

The scene is deliberately **game-agnostic and 2D screen-space** (flat-colored
quads), the smallest common denominator both backends can render identically —
the psyx side via `POLY_F4` + OT, the DX11 side via the draw-command executor
with an orthographic screen→NDC projection. This is the store/load + screenshot
mechanism applied at the renderer level; the full-game in-engine A/B stays a
later integration task.

## Design

- **Common world-state** (`dx11_backendab_state.h`): a small binary blob —
  screen resolution + a list of flat screen-space quads `{x,y,w,h, r,g,b}`.
  Written by `-store`, read by `-load`. Both backends consume it, so the loaded
  frame is rendered from the identical state with no engine iteration.
- **Psyx backend harness** (`dx11_backendab_psyx.cpp`): SDL window + PsyCross
  GPU init, `ClearOTagR` + `setXY4`/`setRGB0`/`addPrim` (`POLY_F4`) + `DrawOTag`,
  framebuffer capture to BMP. Only psyx code.
- **DX11 backend harness** (`dx11_backendab_dx11.cpp`): `Dx11Renderer` +
  `Dx11Res`/`Dx11Tex`/`Dx11Shaders`/`Dx11DrawCmds`, an orthographic screen→NDC
  view-proj, flat opaque draw commands per quad, `CaptureToBMP`. Only DX11 code.
  Also hosts the `-compare` step (game-agnostic BMP + state reader).
- **A/B drive**: psyx `-store` → scene.bin + psyx.bmp; dx11 `-load` → dx11.bmp;
  `-compare` checks each quad's centroid pixel matches its stored color in both
  screenshots.

## Verification

`premake5 gmake2 --os=windows` + `mingw32-make dx11_backendab_{psyx,dx11}
config=release_dev_x86` (32-bit, the game's known-good PsyCross path). Because
the `release_x86` config's `bin/Release/` holds stale MSVC-built `.obj` members,
the harnesses build with `release_dev_x86` (bin/Release_dev, same as the game).

### Binary separation (objdump DLL imports)

```
dx11_backendab_dx11_dev.exe:  DLL d3d11.dll, D3DCOMPILER_47.dll   (NO SDL2/opengl)
dx11_backendab_psyx_dev.exe:  DLL SDL2.dll                       (NO d3d11/dxgi/d3dcompiler)
```

Each binary links only its own backend — the DX11 binary contains no psyx/GL
code, the psyx binary contains no DX11 code.

### Store/load A/B (headless)

```
> dx11_backendab_psyx_dev.exe -store -state scene.bin -shot psyx.bmp   EXIT=0
> dx11_backendab_dx11_dev.exe -load  -state scene.bin -shot dx11.bmp   EXIT=0
> dx11_backendab_dx11_dev.exe -compare -state scene.bin -a psyx.bmp -b dx11.bmp
  A quad0 centroid(32,120)=(214,19,19) expect(220,20,20) PASS
  A quad1 centroid(160,120)=(19,194,39) expect(20,200,40) PASS
  A quad2 centroid(288,120)=(29,58,214) expect(30,60,220) PASS
  B quad0 centroid(32,120)=(220,20,20) expect(220,20,20) PASS
  B quad1 centroid(160,120)=(20,200,40) expect(20,200,40) PASS
  B quad2 centroid(288,120)=(30,60,220) expect(30,60,220) PASS
  COMPARE A_FAILS=0 B_FAILS=0 IDENTICAL=PASS
```

The psyx backend (A) and the DX11 backend (B) both reproduce the identical
scene — same quads, same screen positions, same colors — from the same stored
world-state (`scene.bin`), rendered immediately with no engine iterations.

### Bugs found and fixed during verification

- **psyx OT infinite walk (access violation)**: the `POLY_F4 quad` was a
  loop-local, so all quads shared one stack address → `addPrim` self-linked the
  OT → `ParsePrimitivesLinkedList` walked forever, overflowed `g_vertexBuffer`,
  and segfaulted in `TriangulateQuad`. Fixed by allocating quads outside the
  loop (`POLY_F4 quads[N]`) so each has a distinct linked-list node.
- **psyx black frame**: `glReadPixels` was called after `PsyX_EndScene` (which
  swaps the buffer), reading an undefined backbuffer. Fixed by reading the
  window before `PsyX_EndScene`.
- **DX11 black / shifted quads**: the orthographic screen→NDC projection was
  stored in plain row-vector form (translation in the last row `M[3][0]`), but
  the shader's `mul(pos, viewProj)` reads the CB transposed (`clip = M·pos`), so
  translations must live in the last column `M[0][3]`/`M[1][3]` (the module's
  `P^t` convention). Fixed `MatOrthoScreen`; quads then render in place.
- **DX11 blank quads**: with the ortho y-flip the quad winding reversed, so
  `CULL_BACK` culled them. Fixed by marking the commands `twoSided` (CULL_NONE).
